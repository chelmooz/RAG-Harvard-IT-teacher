# G1.1 — Réserves post-G1 : réseau, installation, kernel/Mesa

**Statut :** à valider par XZ · **Date :** 2026-10-06 · **Gate :** G1.1 (IN PROGRESS)
**Périmètre :** qualification **par preuve documentaire**. Aucune modification système.

---

## 1. Contexte et état constaté

G1 est **CLOSED / ACCEPTED / GREEN** : l'instrumentation, le modèle Qwen2.5-7B-Instruct Q6_K et la chaîne llama.cpp Vulkan sont qualifiés sur le poste de développement (binaire `f0c41e0`, SHA256 modèle `489138df…`, 29/29 couches GPU, buffers device/host séparés).

Trois réserves explicites restent à traiter, plus une incohérence architecturale majeure identifiée lors de l'enquête ADR-003 :

| Réserve | Constat | Cible |
|---------|---------|-------|
| **ADR-003** | `host-gateway` résout vers `172.17.0.1` (docker0) au lieu de `172.30.50.1` (réseau dédié `profia-llama`) | Réseau canonique `172.30.50.0/24`, gateway `172.30.50.1`, nom `llama-host` |
| **INSTALLATION.md** | Absent du dépôt, cité comme référence dans le mandat XZ | Guide complet Debian 13 → BC-250 |
| **Kernel/Mesa** | Debian 13 stable : kernel `6.12.111`, Mesa `25.0.x` ; backports : kernel `7.2.6`, Mesa `25.2.6+` ; cible BC-250 exige kernel `6.18.18`, Mesa `≥25.1` | Stratégie documentée cible vs dev |

**Incohérence architecturale majeure** (découverte pendant l'enquête ADR-003) :

- `docker-compose.yml` : services `ollama`, `backend` (connecte à `ollama:11434`), `postgres`, `frontend`, `nginx`
- `backend/api/config.py` : `OLLAMA_HOST=http://localhost:11434`, pas de `LLAMA_SERVER_URL`
- ADR-002 : **llama.cpp sur l'hôte** via systemd `profia-llama`, pas d'Ollama en conteneur
- Cible v1.4 attendue : `LLAMA_SERVER_URL=http://llama-host:8081` (backend → llama.cpp hôte)

Le dépôt raconte **deux architectures contradictoires** : l'ancienne (Ollama en Docker) encore active dans le code, et la nouvelle (llama.cpp hôte) dans les ADR et le service systemd.

---

## 2. Problème

1. **ADR-003 non résolu** : la résolution `host-gateway → 172.17.0.1` contredit l'ADR qui prescrit `172.30.50.1`. Le mécanisme implicite Docker n'est pas fiable pour la cible canonique `172.30.50.0/24`.

2. **INSTALLATION.md absent** : aucun guide d'installation n'existe pour déployer PROF IA v1.4 sur Debian 13 cible BC-250.

3. **Stratégie kernel/Mesa non documentée** : l'écart entre le poste de dev (kernel 6.12 / Mesa 25.0) et la cible BC-250 (kernel 6.18 / Mesa ≥25.1) n'est pas formalisé avec stratégie de qualification.

4. **Incohérence architecturale non traitée** : le code actif (compose, config) implémente l'ancienne architecture Ollama, alors que les ADR et le systemd définissent la nouvelle architecture llama.cpp hôte. Aucune séparation claire n'existe entre « ce qui est legacy » et « ce qui est la cible ».

---

## 3. Solution

### 3.1 T1 — ADR-003 : résolution réseau explicite

**Décision XZ** : utiliser **explicitement `172.30.50.1`** comme endpoint hôte sur le réseau `profia-llama`, avec `llama-host` comme nom DNS attendu côté backend. **Ne pas dépendre** du mécanisme implicite `host-gateway` de Docker.

Actions :
- Mettre à jour `ADR-003` pour refléter la résolution explicite
- Corriger `docker-compose.yml` : backend utilise `extra_hosts: - "llama-host:172.30.50.1"` (ou variable d'env `LLAMA_SERVER_URL=http://llama-host:8081`)
- Identifier et documenter la migration Ollama → llama.cpp comme **séparée** de la correction réseau
- Lister toutes les références Ollama actives et décider : migration vers llama.cpp ou legacy

### 3.2 T2 — INSTALLATION.md : guide complet Debian 13 → BC-250

Créer `INSTALLATION.md` à la racine du dépôt, structuré en phases :

1. **Prérequis système** (hypothèses cible : kernel 6.18.18, Mesa ≥25.1, Vulkan/RADV, 40 CU, mémoire unifiée 16 Go)
2. **Installation logicielle** : llama.cpp build Vulkan, Docker, docker-compose, systemd `profia-llama`, réseau `profia-llama`, modèle Qwen Q6_K
3. **Configuration** : `.env`, `LLAMA_SERVER_URL`, `extra_hosts`, secrets
4. **Validation post-install** : health checks, test de connectivité hôte↔conteneur, campagne T0.-1 réduite

Distinction explicite à chaque étape : **validé sur dev** / **requis cible** / **à valider sur BC-250** / **non validé**.

### 3.3 T3 — Kernel/Mesa : stratégie documentée

Documenter dans `docs/architecture/DEBIAN13-KERNEL-MESA-STRATEGY.md` (ou section d'`INSTALLATION.md`) :

| Composant | Cible BC-250 | Disponible dev (stable) | Disponible dev (backports) | Stratégie |
|-----------|--------------|------------------------|---------------------------|-----------|
| Kernel    | 6.18.18      | 6.12.111               | 7.2.6                     | Backport 7.x ou compilation ; valider sur BC-250 |
| Mesa      | ≥25.1        | 25.0.x                 | 25.2.6+                   | Backport 25.2+ requis ; valider Vulkan/RADV sur BC-250 |
| 40 CU     | Requis       | Non (24 CU)            | —                         | Patch noyau UMR runtime ; valider `dmesg | grep active_cu_number` |

Chaque ligne : **exigence cible**, **état dev**, **action requise**, **validation BC-250**.

### 3.4 T4 — Incohérence architecturale : séparation réseau vs migration

Produire un document (ADR ou section d'`INSTALLATION.md`) qui :

1. Liste toutes les références **actives** à Ollama dans le code (compose, config, backend, scripts)
2. Identifie lesquelles sont **legacy** (à supprimer) vs **transitoires** (à migrer vers llama.cpp)
3. Sépare explicitement : **correction réseau ADR-003** (cible 172.30.50.1) vs **migration applicative Ollama → llama.cpp** (backend, embeddings, reranker, évaluation)
4. Ne déclare **pas** ADR-003 résolu tant que la documentation active ne raconte pas deux architectures contradictoires
