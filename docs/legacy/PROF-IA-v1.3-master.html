2. Plateforme BC-250 : État Matériel & Qualification

2.1 État matériel retenu

Paramètre Référence du projet Statut
CPU AMD Zen 2, 8 cœurs actifs DÉJÀ FAIT
GPU RDNA2, 40 CU visés À QUALIFIER (Non garanti)
Mémoire 16 Go GDDR6 partagée CPU/GPU MATÉRIEL
UMA 512 Mo minimum / allocation dynamique DÉJÀ CONFIGURÉ
Firmware Firmware modifié via le script Forbidden-Darkness DÉJÀ FAIT
IOMMU Doit rester désactivé selon la documentation BC-250 À VÉRIFIER
Point Critique : 40 CU La configuration firmware prépare le terrain, mais le déverrouillage effectif des 40 CU dépend d'un patch pilote amdgpu expérimental. Toutes les cartes ne sont pas stables à 40 CU.
Conséquence Projet : Aucune optimisation logicielle ne doit supposer les 40 CU acquis. Le système doit fonctionner correctement avec la configuration nominale (souvent 24-32 CU détectés) et gagner en performance si le patch tient. La qualification thermique et de stabilité est une étape bloquante avant la production.

2.2 Important sur les 512 Mo

Le réglage 512 Mo ne signifie pas « seulement 512 Mo de VRAM ». Il définit la mémoire minimale réservée côté UMA ; la mémoire GPU peut être utilisée dynamiquement au-delà de cette valeur. La documentation explique également que les limites dynamiques Linux peuvent nécessiter une configuration TTM si l’on veut pousser la consommation VRAM plus haut.

3. Debian 13 et validation GPU

Le projet cible Debian 13 bare metal. Nous conservons Debian car c’est le choix du projet, mais les versions réelles de kernel/Mesa doivent être validées avant d’aller plus loin.

3.1 Contraintes BC-250 à respecter

  • Kernel : préférer une version validée par la documentation BC-250 ; 6.18.18 LTS est recommandé.
  • Mesa : 25.1.3+ minimum indiqué ; 25.3.x recommandé.
  • IOMMU : désactivé.

3.2 Validation minimale après installation

uname -a
cat /proc/cmdline
lscpu
lspci -nn | grep -Ei 'VGA|Display|AMD'
free -h
dmesg | grep -i amdgpu
vulkaninfo --summary
# Vérifier le nombre de CU réellement exposés par le driver
vulkaninfo --summary | grep -i computeUnits

Critères :

  • 8 cœurs visibles par lscpu.
  • GPU AMD détecté par PCI.
  • RADV/Vulkan détecté sans erreur critique.
  • Pas de boucle de reset GPU dans dmesg.

3.3 Vulkan/RADV contre ROCm

BC-250
├── RADV / Vulkan
│   └── llama.cpp → Gemma 4
│
└── ROCm / PyTorch (OPTIONNEL)
    ├── BGE-M3
    ├── bge-reranker-v2-m3
    └── Whisper

Décision : llama.cpp reste sur Vulkan/RADV. Pour les workloads PyTorch, on mesure CPU contre ROCm ; on ne déduit pas leur placement à l’avance.

Elle prescrit 172.17.0.1, adresse de l'interface docker0 par défaut, qui n'est pas garantie. v1.4 impose un réseau déclaré profia-llama (172.30.50.0/24, passerelle 172.30.50.1) et une résolution par host-gateway. Puisque llama-server tourne directement sur l'hôte (pour gérer Vulkan/Mémoire finement) et FastAPI dans Docker :
  • Ne pas utiliser 127.0.0.1 depuis le conteneur (cela pointerait vers le conteneur lui-même).
  • Configurer llama-server pour écouter sur l'adresse IP de l'interface bridge Docker de l'hôte (par défaut 172.17.0.1 sur Debian/Linux standard, ou vérifier avec ip addr show docker0).
  • Dans le fichier .env du backend : LLAMA_SERVER_URL=http://172.17.0.1:8081.
  • Sécurité : Utiliser les pare-feux locaux (nftables/iptables) pour restreindre l'accès à ce port uniquement depuis le sous-réseau Docker, interdisant l'accès LAN direct.

5.2 Installation & Compilation (Corrigé)

Pour permettre le téléchargement simplifié via -hf, la compilation doit inclure le support CURL. Cependant, pour une robustesse maximale hors-ligne ou reproductible, le téléchargement manuel est préféré.

Option A : Compilation avec Support HF (Simple)

# Installer les dépendances
sudo apt-get install git cmake build-essential libcurl4-openssl-dev

git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
# IMPORTANT : LLAMA_CURL=ON est requis pour utiliser l'argument -hf
cmake -B build -DGGML_VULKAN=ON -DLLAMA_CURL=ON
cmake --build build --config Release -j$(nproc)

Option B : Téléchargement Manuel & Chemin Local (Recommandé Prod)

# Télécharger le modèle manuellement
mkdir -p /opt/models
wget https://huggingface.co/bartowski/google_gemma-4-26B-A4B-it-GGUF/resolve/main/google_gemma-4-26B-A4B-it-IQ3_XS.gguf \
  -O /opt/models/gemma-4-26B-iq3_xs.gguf

# La compilation n'a alors pas besoin de CURL, mais on garde ON par compatibilité future
cmake -B build -DGGML_VULKAN=ON -DLLAMA_CURL=ON
cmake --build build --config Release -j$(nproc)

5.3 Commande de départ — à benchmarker

Si Option B (Local) est choisie :

llama-server \
  -m /opt/models/gemma-4-26B-iq3_xs.gguf \
  -ngl 999 \
  -c 8192 \
  -ctk q4_0 \
  -ctv q4_0 \
  -fa on \
  -b 512 \
  -ub 512 \
  -np 1 \
  --jinja \
  --host 172.17.0.1 \
  --port 8081
Attention sur -ngl 999 -ngl 999 demande l'offload maximal des couches sur le GPU. Cela ne garantit pas que tout tiendra en mémoire, surtout avec le partage UMA.
Action : Après lancement, vérifier les logs llama-server. Si des erreurs d'allocation apparaissent ou si la vitesse chute drastiquement (swapping), réduire -ngl progressivement (ex: 40, puis 30...) jusqu'à trouver le point stable. Ne pas considérer 999 comme magique.

Reproductibilité : Épingler le commit hash de llama.cpp dans deploy/llama/VERSION.

10.1 Tables conceptuelles (Mise à jour v1.3)

-- Table principale pour stocker les échanges
CREATE TABLE responses (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID NOT NULL,
    user_query TEXT NOT NULL,
    assistant_answer TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    metadata JSONB -- Peut contenir le RetrievalPlan brut
);

CREATE TABLE documents (...);
CREATE TABLE document_chunks (...);
CREATE TABLE wiki_documents (...);

-- Liens vers responses.id
CREATE TABLE response_evaluations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    response_id UUID REFERENCES responses(id) ON DELETE CASCADE,
    judge_score FLOAT,
    devil_score FLOAT,
    groundedness BOOLEAN,
    completeness FLOAT,
    citation_validity FLOAT,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE TABLE human_feedback (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    response_id UUID REFERENCES responses(id) ON DELETE CASCADE,
    human_rating INT CHECK (human_rating BETWEEN 1 AND 5),
    human_comment TEXT,
    is_golden BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

10.2 Recherche vectorielle

pgvector est utilisé pour la recherche dense. PostgreSQL FTS fournit le signal lexical. Les deux sont fusionnés avant reranking.

16.1 Conteneurs (Backend/Front/DB)

16.2 llama.cpp sur l'Hôte (Systemd)

⚠ SUPERSEDED (v1.4) — l'unité de service ci-dessous est caduque. Elle écoute sur 172.17.0.1 (bridge docker0 par défaut, adresse non garantie). v1.4 impose 172.30.50.1 sur le réseau déclaré profia-llama. Le service v1.4 en vigueur est deploy/systemd/profia-llama.service de ce dépôt, et il ne doit pas poser MemoryDenyWriteExecute=true (casse le JIT Vulkan). Voir docs/architecture/adr/ADR-003-network-host-gateway.md et ADR-002-llama-cpp-vulkan-gemma4.md.

Créer le service /etc/systemd/system/profia-llama.service.

[Unit]
Description=Gemma 4 llama.cpp server
After=network-online.target
Wants=network-online.target

[Service]
User=profia
Group=profia
WorkingDirectory=/opt/llama.cpp/build/bin
# Assurez-vous que le chemin du modèle existe (Voir Section 5.2 Option B)
ExecStart=/opt/llama.cpp/build/bin/llama-server \
  -m /opt/models/gemma-4-26B-iq3_xs.gguf \
  -ngl 999 \
  -c 8192 \
  -ctk q4_0 \
  -ctv q4_0 \
  -fa on \
  -b 512 \
  -ub 512 \
  -np 1 \
  --jinja \
  --host 172.17.0.1 \
  --port 8081
Restart=on-failure
RestartSec=5
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
Vérification Post-Installation 1. Démarrer le service : systemctl start profia-llama 2. Vérifier l'écoute : ss -tlnp | grep 8081 (doit montrer 172.17.0.1:8081) 3. Tester depuis le conteneur backend : docker exec -it curl http://172.17.0.1:8081/health

A.3 Points de Vigilance Techniques

1. Sécurité & Données Sensibles : Comme l'utilisateur est prudent concernant l'accès des agents d'IA aux données personnelles sensibles, assure-toi que le pipeline d'ingestion nettoie bien les PII (Personally Identifiable Information) avant l'embedding, ou configure PostgreSQL pour chiffrer les colonnes sensibles. L'accès au serveur llama.cpp reste strictement localhost (127.0.0.1).
⚠ SUPERSEDED (v1.4) — la dernière phrase est fausse pour cette architecture et contredit les §4 et §16 de ce même document. Depuis un conteneur, 127.0.0.1 désigne le conteneur, jamais l'hôte : le backend ne peut donc pas joindre llama-server ainsi. v1.4 impose l'écoute sur l'interface bridge d'un réseau Docker dédié et une résolution host-gateway — voir docs/architecture/adr/ADR-003-network-host-gateway.md. Le filtrage réseau local (nftables/iptables) reste la responsabilité du déploiement.
2. Stabilité BC-250 : Le passage à Gemma 26B est lourd. Si tu observes des crashes GPU (reset cycles), reviens immédiatement à une configuration partielle (ex: désactiver l'unlock 40 CU ou réduire le contexte à 4096 tokens) plutôt que de tenter de "forcer" la stabilité. La documentation insiste sur la qualification progressive.
3. Reproductibilité : Épingle la version exacte de llama.cpp (commit hash) dans ton repo. Ne laisse pas le serveur se mettre à jour automatiquement. Cela garantit que les benchmarks et les résultats sont comparables dans le temps.
4. Coût Calculatoire : Le reranking (bge-reranker-v2-m3) est coûteux. Assure-toi qu'il ne tourne pas simultanément avec la génération LLM si la mémoire VRAM partagée est saturée. Séquence les opérations : Retrieval -> Rerank (CPU/GPU léger) -> Generation (GPU lourd).
